# How to get third-party credentials for `.env.<environment>`

Run `pnpm github:sync` once to generate missing `.env.<environment>` files
(both **gitignored**) from the committed `.env.example` template (environments listed in `tooling/setup/setup.config.json`). Then edit
each file with the values from the per-provider sections below. Push to GitHub
with `pnpm github:sync <environment>` when ready. **Never commit any `.env.*`
file other than `.env.example`.**

The full workflow (Secret vs Variable classification, adding/renaming/removing
keys, validation matrix, troubleshooting) lives in
**[environment-variables.md](../deployment/runbooks/environment-variables.md)**.
This page is the **credentials catalogue** — it tells you where each third-party
value comes from. It does NOT teach the workflow.

---

```mermaid

  end

    Resend[Resend: mail]
    OAuth[OAuth: Google, Apple]
    Stripe[Stripe: billing]
    Sentry[Sentry: errors]
    Postman[Postman: docs upload]
    Scalar[Scalar: docs registry]
    Instagram[Instagram: automation]
  end

  required --> env_file[".env.&lt;environment&gt; at project root\n(gitignored, generated by pnpm github:sync)"]
  optional --> env_file
  env_file -- pnpm github:sync --> github[GitHub Environment\n(Secrets + Variables)]
```

Required vs optional credentials and where they go: local
`.env.<environment>`, then pushed to GitHub Environments by `pnpm github:sync`,
then pulled by the deploy workflow at release time. The per-service guides
below show where the value comes from; the runbook above shows the workflow.

## 1. S3 (AWS) — uploads / presigned URLs

**Used for:** uploads (presigned PUT/POST, confirm-time HEAD + magic-byte read + publish copy), avatars and organization logos, GDPR data exports, the audit cold export, and the retention jobs that delete objects.

| .env variable          | Where to get it                 |
| ---------------------- | ------------------------------- |
| `S3_BUCKET`            | Bucket name you create.         |
| `S3_REGION`            | Region code (e.g. `us-east-1`). |
| `S3_ACCESS_KEY_ID`     | IAM user access key.            |
| `S3_SECRET_ACCESS_KEY` | IAM user secret key.            |

**Steps (AWS Console):**

1. Go to [AWS Console](https://console.aws.amazon.com/) → **S3** → **Create bucket**.
2. Pick a name (e.g. `myapp-uploads-dev`), choose region (e.g. `us-east-1`), create.
3. Go to **IAM** → **Users** → **Create user** (e.g. `s3-upload-app`).
4. Attach an inline policy with exactly these permissions (replace the bucket name):

   ```json
   {
     "Version": "2012-10-17",
     "Statement": [
       {
         "Effect": "Allow",
         "Action": ["s3:GetObject", "s3:PutObject", "s3:DeleteObject"],
         "Resource": "arn:aws:s3:::myapp-uploads-dev/*"
       },
       {
         "Effect": "Allow",
         "Action": "s3:ListBucket",
         "Resource": "arn:aws:s3:::myapp-uploads-dev"
       }
     ]
   }
   ```

   - `s3:ListBucket` is **required**, not optional: without it S3 answers a HEAD or GET for a
     missing key with **403 AccessDenied** instead of 404. The app can only treat a 403 as storage
     failing — an upload whose object never landed then stays PENDING forever instead of failing,
     the pending-upload sweep never removes it, and the 403s count against the S3 circuit.
   - `s3:DeleteObject`: confirm removes the pending copy, and offboarding plus the retention jobs
     delete objects — a retention row is deleted only once its object is, so without this
     permission tombstoned rows are never purged.
   - `s3:GetObject` + `s3:PutObject` also cover the server-side copy that publishes a confirmed
     upload (read the source, write the destination).
5. **Security credentials** → **Create access key** → choose "Application running outside AWS" → create.
6. Copy **Access key ID** → `S3_ACCESS_KEY_ID`; **Secret access key** → `S3_SECRET_ACCESS_KEY`.
7. In `.env`:  
   `S3_BUCKET=myapp-uploads-dev`  
   `S3_REGION=us-east-1`  
   (plus the two keys above.)

**CLI (optional):** [AWS CLI](https://aws.amazon.com/cli/) — `aws s3 mb s3://myapp-uploads-dev`, then create user/keys in console or with `aws iam create-user` / `aws iam create-access-key`.

## 2. Resend — email (email verification-code, invitations)

**Used for:** Email verification-code login, invitations, account-security notices.

| .env variable        | Where to get it                            |
| -------------------- | ------------------------------------------ |
| `RESEND_API_KEY`     | Resend API key.                            |
| `EMAIL_FROM_ADDRESS` | Sender email (required when `RESEND_API_KEY` is set; must be verified in Resend — no hardcoded fallback). |

**Steps:**

1. Sign up at [resend.com](https://resend.com).
2. **API Keys** → **Create API Key** → copy key (starts with `re_`) → `RESEND_API_KEY`.
3. **Domains** → add your domain (or use their sandbox domain for testing).

5. In `.env`:  
   `RESEND_API_KEY=re_xxxx`  
   `EMAIL_FROM_ADDRESS=noreply@yourdomain.com` (required whenever `RESEND_API_KEY` is set)  
   `EMAIL_FROM_NAME=YourApp`

**CLI:** Resend has no official credential CLI; use the dashboard.

## 3. OAuth — Google (login with Google)

**Used for:** `GET /api/v1/auth/oauth/:provider` (redirect to Google). Without these, Google is left out of `GET /auth/oauth/providers` and its start returns 404.

| .env variable                | Where to get it                          |
| ---------------------------- | ---------------------------------------- |
| `OAUTH_GOOGLE_CLIENT_ID`     | Google OAuth client ID.                  |
| `OAUTH_GOOGLE_CLIENT_SECRET` | Google OAuth client secret.              |
| `OAUTH_GOOGLE_REDIRECT_URI`  | Callback URL (must match Google config). |

**Steps:**

1. Go to [Google Cloud Console](https://console.cloud.google.com/) → **APIs & Services** → **Credentials**.
2. **Create Project** (if needed) → **OAuth consent screen** → External (or Internal) → fill app name, save.
3. **Credentials** → **Create credentials** → **OAuth client ID**.
4. Application type: **Web application**.
5. **Authorized redirect URIs** add: `http://localhost:3000/auth/oauth/google/callback` (or your API base + `/auth/oauth/google/callback`).
6. Create → copy **Client ID** and **Client secret**.
7. In `.env`:  
   `OAUTH_GOOGLE_CLIENT_ID=xxxx.apps.googleusercontent.com`  
   `OAUTH_GOOGLE_CLIENT_SECRET=xxxx`  
   `OAUTH_GOOGLE_REDIRECT_URI=http://localhost:3000/auth/oauth/google/callback`

## 4. OAuth — Apple (Sign in with Apple)

**Used for:** Sign in with Apple (`GET /api/v1/auth/oauth/apple`, Apple's form post to `POST /api/v1/auth/oauth/apple/callback`, then `GET /api/v1/auth/oauth/apple/callback`). Set all five or none: without them Apple is left out of `GET /auth/oauth/providers` and its start returns 404; a half-set group fails at boot.

| .env variable            | Where to get it                                                                                                   |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `OAUTH_APPLE_CLIENT_ID`    | The **Services ID** identifier (e.g. `com.example.web.signin`).                                                    |
| `OAUTH_APPLE_TEAM_ID`      | Your Apple developer **Team ID**.                                                                                 |
| `OAUTH_APPLE_KEY_ID`       | The **Key ID** of the Sign in with Apple key.                                                                     |
| `OAUTH_APPLE_PRIVATE_KEY`  | The key's `.p8` file content (PEM; newline escapes accepted) — a Secret; it signs each swap's ES256 client secret. |
| `OAUTH_APPLE_REDIRECT_URI` | The public URL of `POST /api/v1/auth/oauth/apple/callback` on THIS API (Apple posts its form there).                |

**Steps:**

1. Apple Developer → **Certificates, Identifiers & Profiles** → **Identifiers** → an App ID with **Sign in with Apple** on.
2. **Identifiers** → **Services IDs** → new Services ID → enable **Sign in with Apple** → **Configure**: the primary App ID, the domain of the API, and as **Return URL** `https://api.example.com/api/v1/auth/oauth/apple/callback` (Apple requires https; it must equal `OAUTH_APPLE_REDIRECT_URI`).
3. **Keys** → new key with **Sign in with Apple** → download the `.p8` once, note the **Key ID**.
4. To send email to private relay addresses, register the sending domain under **Services** → **Sign in with Apple for Email Communication**.
5. In `.env`: the five `OAUTH_APPLE_*` values above.

The API answers Apple's form with a `303` to `<FRONTEND_URL>/callback/apple?code&state` (or `?reason=` on a failure), so `FRONTEND_URL` must be the app's origin.

---

**Production smoke (after secrets are in Railway / GitHub Environment):**

1. Set `FRONTEND_URL` to the deployed frontend origin (used for default redirect URIs when `OAUTH_*_REDIRECT_URI` is unset).
2. Confirm OAuth app callback URLs match **exactly** the values in env (scheme, host, path).
3. API checks (replace host):

   ```bash
   curl -sS -o /dev/null -w "%{http_code}\n" https://api.example.com/api/v1/auth/oauth/providers
   # Expect 200

   curl -sS -o /dev/null -w "%{http_code}\n" https://api.example.com/api/v1/auth/oauth/google
   # Expect 200 (redirect_url to Google) when Google is configured; 404 when not

   curl -sS -o /dev/null -w "%{http_code}\n" https://api.example.com/api/v1/auth/oauth/apple
   # Expect 200 (redirect_url to Apple) when the five OAUTH_APPLE_* are set; 404 when not
   ```

4. Complete one browser callback flow per provider and verify session cookie + JWT are issued.

Implementation lives under `src/domains/auth/sub-domains/auth-method/oauth/` — no code change is required to enable providers; only env + OAuth app configuration.

## 5. Stripe — billing / subscriptions / webhooks

**Used for:** Plans, subscriptions, webhook handling.

| .env variable           | Where to get it                                      |
| ----------------------- | ---------------------------------------------------- |
| `STRIPE_SECRET_KEY`     | Stripe secret key (test: `sk_test_...`).             |
| `STRIPE_WEBHOOK_SECRET` | Webhook signing secret (for local: from Stripe CLI). |

**Production requires both.** A production boot refuses to start unless `STRIPE_SECRET_KEY` is the
live key (`sk_live_…`) and `STRIPE_WEBHOOK_SECRET` is the signing secret of the production webhook
endpoint (Option B below, pointed at the production API) — set both as Secrets in the `production`
GitHub Environment (`.env.production` + `pnpm github:sync production`). Locally and in development
both may stay unset: subscriptions are then recorded locally and never charged.

**Steps (Dashboard):**

1. Sign up at [stripe.com](https://stripe.com) → **Developers** → **API keys**.
2. Copy **Secret key** (test) → `STRIPE_SECRET_KEY=sk_test_xxxx`.

**Price the plans (sandbox):** `pnpm db:seed` installs the plan catalog without Stripe prices, and
`POST /billing/subscriptions` refuses a plan with no price for its cycle (`422
planNotAvailableForBillingCycle`). With a test-mode key set, `pnpm db:seed:stripe-catalog` gives
every paid plan its Stripe product and monthly and yearly prices, and records their ids on the plans
(`--dry-run` says what it would do). It refuses a live key, and a re-run creates nothing. Free gets
no price: an organization with no subscription is on Free, it never subscribes to it.

**Webhook secret (for local / tests):**

- **Option A — Stripe CLI (recommended for local):**
  1. Install [Stripe CLI](https://stripe.com/docs/stripe-cli): `brew install stripe/stripe-cli/stripe` (macOS) or see docs.
  2. Login: `stripe login`.
  3. Forward webhooks to your server: `stripe listen --forward-to localhost:3000/api/v1/billing/webhook`.
  4. CLI prints **webhook signing secret** (`whsec_...`) → `STRIPE_WEBHOOK_SECRET=whsec_xxxx`.
- **Option B — Dashboard:** **Developers** → **Webhooks** → **Add endpoint** → URL e.g. `https://your-api.com/api/v1/billing/webhook` → select events → create → reveal **Signing secret** → `STRIPE_WEBHOOK_SECRET=whsec_xxxx`.

**Test the subscription webhook flow (local):** with `stripe listen` running (Option A), the API
ingests exactly the three subscription lifecycle events — `customer.subscription.created`,
`customer.subscription.updated`, `customer.subscription.deleted` (the switch in
[`stripe-webhook.service.ts`](../../src/domains/billing/sub-domains/stripe-webhook/stripe-webhook.service.ts)).
`past_due` / `active` transitions arrive as `status` on `.updated`; there is **no** separate
`invoice.*` handler.

1. **Run the worker** — webhook receipt only **enqueues**; nothing is processed unless the BullMQ
   worker runs. In a second terminal (alongside `pnpm dev`): `pnpm dev:worker`.
2. **Trigger events** — in a third terminal:

   ```bash
   stripe trigger customer.subscription.created
   stripe trigger customer.subscription.updated
   stripe trigger customer.subscription.deleted
   ```

3. **Verify** — each delivery writes a row to `billing.stripe_webhook_events` (the idempotency
   ledger), and `billing.subscriptions` reflects the new `status`. If `stripe listen` prints
   `200` but no rows appear, the worker from step 1 isn't running.

## 7. Monthly restore drill — Neon API

**Used for:** [Monthly backup restore & RTO drill](../process/backup-drills.md) workflow ([scheduled-monthly-restore-rto.yml](../../.github/workflows/scheduled-monthly-restore-rto.yml)).

These are **GitHub Environment secrets** (not API/worker runtime vars). Add them to `.env.development` / `.env.production` under the GitHub Secrets half and push with `pnpm github:sync`. The scheduled workflow uses the Neon API to create a PITR child branch in the Neon project of the **GitHub Environment** the run resolves to (`main` → **`production`** → project **`meepzo-be-production`**).

| Secret | Where to get it |
| --- | --- |
| `MONTHLY_DATABASE_RESTORE_DRILL_NEON_API_KEY` | Written by the infrastructure repository's setup (its `NEON_API_KEY`); or Neon Console → **Organization settings → API keys** ([key types](https://neon.com/docs/manage/api-keys)) |

An **organization** API key is preferred. A personal key works too: on an organization-owned project the Neon API answers `org_id is required`, so the drill looks up the key's organization and asks again — it fails only when the key belongs to several organizations.

Every Neon name derives from the environment — one Neon project per environment, the infrastructure repository's rule (project ID is **not** a secret; override the project with `RESTORE_DRILL_NEON_PROJECT_NAME` only if yours differs):

| | development | production |
| --- | --- | --- |
| Neon project | `meepzo-be-development` | `meepzo-be-production` |
| Branch (the drill's parent) | `development` | `production` |
| Database | `meepzo_be_development` | `meepzo_be_production` |
| Owner (the drill branch's login) | `meepzo_be_development_owner` | `meepzo_be_production_owner` |

Without the secret, the monthly workflow **fails**.

## 10. Meta — Instagram automation (the Meta app, Unified Login)

**Used for:** connecting an organization's business portfolio through Meta's Unified Login (Facebook Login for
Business — one login for Instagram, Facebook Pages and ads), every Graph call's `appsecret_proof`, and checking Meta's
signed requests and the Instagram webhook's `X-Hub-Signature-256`. Every call goes through the one Meta client
(`src/domains/app/sub-domains/channel-connection/channel-connection-meta/`). All five settings are optional in every
environment, production included, and the app still boots without them: each Instagram route that needs one of the
four app settings answers `503 instagram_not_configured` (Meta's deauthorize and data-deletion callbacks need only
`META_APP_SECRET`), and without the webhook's verify token Meta's subscription check answers
`503 instagram_webhook_not_configured`. An app secret or a verify token that is set must be at least 32 characters, or
the app does not boot: the secret is the key that proves Meta signed a request, so a placeholder left in an environment
stops the boot instead of letting anyone sign a delivery. `.env.example` ships both blank. (The connect routes moved to
Unified Login with ROUTE row R3 of `iterations/feat-instagram-dm-sending-2026-11-23-oxak/`; the launch's Instagram Login
connect, its hosts and its scopes are gone.)

| .env variable            | Where to get it                                                                                     |
| ------------------------ | --------------------------------------------------------------------------------------------------- |
| `META_APP_ID`       | **App ID** (App settings → Basic; a GitHub Variable — it is public, the `client_id` of the login address). |
| `META_APP_SECRET`   | **App secret** (App settings → Basic; a GitHub Secret, at least 32 characters — Meta's are 32) — the one secret for the code exchange, `appsecret_proof` and both signatures. Unset, every route that needs it answers 503. |
| `META_CONFIG_ID`    | **Configuration ID** of the Facebook Login for Business configuration (a GitHub Variable — not secret): which permissions and assets the login asks for. |
| `META_REDIRECT_URI` | The frontend's `/auth/meta/callback` page (a GitHub Variable), registered on the app exactly.  |
| `META_WEBHOOK_VERIFY_TOKEN` | **You choose it** (a GitHub Secret, at least 32 characters — e.g. `openssl rand -hex 32`) and type it as the webhook's **Verify token** (step 5); Meta sends it back as `hub.verify_token`. Unset, Meta's subscription check answers `503 instagram_webhook_not_configured`. |

**Steps (Meta App Dashboard):**

1. [developers.facebook.com/apps](https://developers.facebook.com/apps) → create (or open) a
   **Business** app with the Instagram use case and **Facebook Login for Business**.
2. **App settings** → **Basic** → copy **App ID** → `META_APP_ID` and **App secret** →
   `META_APP_SECRET`.
3. **Facebook Login for Business** → **Configurations** → create a configuration (system-user
   token, the Instagram accounts and the permissions below) → copy its **Configuration ID** →
   `META_CONFIG_ID`. **Settings** → **Valid OAuth redirect URIs**: add the frontend callback of every
   environment — e.g. `https://app.example.com/auth/meta/callback` — and put that environment's one
   value in `META_REDIRECT_URI`. It must match character for character: the code exchange sends it
   again. For a local frontend, register `http://localhost:5173/auth/meta/callback` (the
   `.env.example` value), or a public https tunnel address if the dashboard refuses it.
4. **App Review** → **Permissions and features**: the three permissions connect needs (below).
   Until the app has Advanced Access to them, only people with a role on the app (**App roles**)
   can log in and connect their business's Instagram accounts.
5. **Webhooks** → the **Instagram** object → **Subscribe to this object**: **Callback URL**
   `https://<api host>/api/v1/app/social/channel-connections/meta/webhooks/instagram` and **Verify token** the value of
   `META_WEBHOOK_VERIFY_TOKEN` → **Verify and save** (Meta calls `GET …/webhook` with
   `hub.mode=subscribe`, the token and a challenge; the API echoes the challenge). Then subscribe the
   app to the three webhook fields (below). Meta signs each delivery (`POST …/webhook`) with
   `X-Hub-Signature-256` — the HMAC of the raw body with `META_APP_SECRET`.
6. **Facebook Login for Business** → **Settings**: set the
   **Deauthorize callback URL** to `https://<your API host>/api/v1/app/social/channel-connections/meta/deauthorize`;
   **App settings** → **Basic**: set the **Data deletion request URL** to
   `https://<your API host>/api/v1/app/social/channel-connections/meta/data-deletion`. Meta posts a form with one
   `signed_request` there, signed with `META_APP_SECRET`: the first disconnects the accounts the
   signed id reaches — the account of that id in every organization holding it, else every account
   of that business's connections — the second also erases their profiles and stored posts and answers
   Meta with a confirmation code and a status link to the frontend's `/instagram/data-deletion`
   page (`FRONTEND_URL`). Without `META_APP_SECRET` both answer
   `503 instagram_not_configured`.

**The redirect URI, one per environment.** Each value is the frontend's
`/auth/meta/callback` page of that environment, and each must also be listed under the app's
**OAuth redirect URIs** (step 3):

| Environment | `META_REDIRECT_URI` | Set in |
| --- | --- | --- |
| local | `http://localhost:5173/auth/meta/callback` (the `.env.example` value) | `.env.local` |
| development | the development frontend's `https://…/auth/meta/callback` | `.env.development`, pushed with `pnpm github:sync development` |
| production | the production frontend's `https://…/auth/meta/callback` | `.env.production`, pushed with `pnpm github:sync production` |

The hosted values — all five settings — reach their GitHub Environment only through
`pnpm github:sync <environment>`: `META_APP_SECRET` and `META_WEBHOOK_VERIFY_TOKEN` as
Secrets, `META_APP_ID`, `META_CONFIG_ID` and `META_REDIRECT_URI` as Variables (their half of `.env.example`
decides which).

**The permissions connect needs** (`META_REQUIRED_PERMISSIONS` in
`channel-connection.constants.ts`). The login configuration (`META_CONFIG_ID`) asks for them, and the login must grant
all three; one left unticked on Meta's consent screen answers `422 provider_permissions_missing` and saves nothing.
`ads_read` is optional — without it the ad picker is empty:

| Permission | Why |
| --- | --- |
| `instagram_basic` | the account read, the posts, reels and stories |
| `instagram_manage_messages` | direct messages, private replies to comments, story replies and the follow check |
| `instagram_manage_comments` | reading comments and replying to them publicly |
| `ads_read` (optional) | the ad picker's ad accounts and ads |

**The webhook fields.** Every connect subscribes the account to `comments`, `messages` and
`messaging_postbacks` (`INSTAGRAM_WEBHOOK_SUBSCRIBED_FIELDS` in the Instagram client, through
`POST /{instagram_user_id}/subscribed_apps`); a failed subscription is retried by the next
connect, the account set-up's tries and the 10-minute webhook subscription check (R40). The app itself must be subscribed to the
same three fields (step 5), or no event arrives.

**Locally:** `pnpm setup:local` copies `META_APP_ID`, `META_APP_SECRET` and `META_CONFIG_ID` from
`.env.development` (or your environment variables) while `.env.local` still holds the
`.env.example` placeholder — the secret is blank there, and an older file's `...` (refused as too
short) is set back to blank; `META_REDIRECT_URI` is per environment and is never copied, and
`META_WEBHOOK_VERIFY_TOKEN` is yours to choose, at least 32 characters (`.env.example` leaves it
blank, so the subscription check answers 503 until you set one; a webhook pointed at your machine
through a tunnel is verified with whatever token you typed into the dashboard). Tests never use these: the
harness sets a fake Meta app and a test verify token, and refuses every outside host.

## Quick checklist (paste into `.env.development`)

After you have the values, drop them into `.env.development` (created by
`pnpm github:sync`). Keep each key under the half + sub-section it already lives
in — that placement is what `pnpm github:sync` reads when classifying. The
ordering and grouping below mirrors `.env.example`:

```bash
# --- under # GitHub Secrets ---
DATABASE_URL=postgresql://...
DATABASE_MAINTENANCE_URL=postgresql://...   # same host, user meepzo_be_maintenance
REDIS_URL=redis://...
JWT_PRIVATE_KEY=-----BEGIN PRIVATE KEY-----\n...\n-----END PRIVATE KEY-----  # gitleaks:allow
SECRETS_ENCRYPTION_KEY=<64 hex chars; node -e "console.log(require('crypto').randomBytes(32).toString('hex'))">
RESEND_API_KEY=re_...
OAUTH_GOOGLE_CLIENT_SECRET=...
```
