# Response-code policy (meepzo-be)

When to set which HTTP status — the single contract every route, test, and doc follows. The policy is **enforced in code**, not by convention: the success side by `src/shared/middlewares/core/method-status-policy.middleware.ts` plus the route-status gates, the documented error side by `tooling/openapi/emitters/responses-builder.ts`.

---

## Success statuses — by method, never per-handler

| Method      | Status  | Meaning                                                                                                                                              |
| ----------- | ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET         | **200** | Resource(s) returned.                                                                                                                                |
| POST        | **200** | Success — including creates, idempotent replays, and upserts (where a fixed 201 would lie on the replay). The central `onSend` hook rewrites any 201/202/204 a POST handler produced to 200 — controllers never hand-pick. |
| PUT / PATCH | **200** | Updated resource returned.                                                                                                                           |
| DELETE      | **204** | Deleted/revoked; no body.                                                                                                                            |

**No exemptions:** the Stripe webhook's 200 acknowledgement is simply the policy, and `POST /api/v1/mcp` answers through `reply.hijack()`, which bypasses the hook, so the MCP streamable-HTTP transport owns its status codes.

**Success bodies outside the `{ data, meta }` envelope** — a provider that reads its own answer shape gets it as it is (the route's `raw_response` config, which `response-format.middleware.ts` honours); the status is still the method's: `POST /api/v1/app/social/instagram/data-deletion` (Meta's data-deletion callback, launch routes-final § 1.D, IA20) answers Meta's documented `{ "url": "<FRONTEND_URL>/instagram/data-deletion?code=<code>", "confirmation_code": "<code>" }` with `200` — Meta reads the two keys at the top level. Its sibling `POST /api/v1/app/social/instagram/deauthorize` keeps the envelope (`{ data: null, meta }`; Meta reads only the status). Both are PUBLIC, form-encoded (`application/x-www-form-urlencoded`, a body of any other type is `415`), take no `X-Idempotency-Key`, and answer `200` once the signed request verifies — also for a person never stored, or a repeat — so Meta does not retry.

**PUT vs PATCH, and action verbs:** PUT replaces a resource in full; PATCH merges a partial update (both → 200). A collection-level action that has no target id is a `POST /collection/verb` (e.g. `POST /tenancy/organization/transfer-ownership`); a single-resource state change is a `PATCH /resource/:id/state` (or a dedicated action sub-path). Don't model a named action as a bare PUT/PATCH on the parent resource when it has its own verb.

**Where the truth lives and how it is enforced:**

1. Declared: `tooling/openapi/route-catalog/route-success-statuses.json` — one entry per route; `pnpm validate:route-success-statuses` keeps it in sync with `docs/routes.txt`.
2. Enforced at runtime: the method-status middleware (above).
3. Observed: `pnpm validate:route-success-coverage` after a full `pnpm test` fails CI on declared-vs-observed drift.
4. Documented: the OpenAPI responses builder reads the registry — the spec can never disagree with the declared status.

**Adding a route:** pick the status from the method table (don't invent), run `pnpm routes:catalog`, add the registry entry, write the happy-path test asserting that status.

## Error statuses — when each one applies

| Status  | Use when                                                                                                                                                                                                                                                                                                                                                                                              | Emitted by                                       |
| ------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| **400** | Request shape is invalid — body field, path param, or query param fails Zod validation (response carries per-field `errors: [{ field, message }]`), malformed JSON hits the parser, or a webhook signature fails. Documented on every POST/PATCH/PUT and on any route with path or query params; **omitted entirely** only on param-less, query-less GET/DELETE (nothing to validate).               | Validators / Zod type provider / Fastify parser  |
| **401** | `Authorization` header missing, malformed, or carries an expired/revoked access token. Message tells the developer how to recover (login → `Authorization: Bearer <ACCESS_TOKEN>`).                                                                                                                                                                                                                   | Auth middleware                                  |
| **403** | Authenticated but not allowed: missing organization permission, role too low, suspended membership, a product write from a read-only organization (`organization_read_only`).                                                                                                                                                                                                                                                                                                   | Permission guards                                |
| **404** | Resource id (or route) does not exist — including ids of the right shape but no row, and ids that belong to another organization (no existence leak). A team-only read on a personal organization answers 404 too, with `reason: team_organization_required` (a read is never a 422).                                                                                                                 | Services / repositories                          |
| **406** | MCP route only — `Accept` header missing or names an unsupported media type.                                                                                                                                                                                                                                                                                                                          | MCP transport                                    |
| **409** | Mutating routes — state conflict: duplicate resource (slug/email already taken), invalid state transition, an in-flight duplicate request with the same `X-Idempotency-Key`, a billing record the payment provider no longer has (`reason: payment_provider_resource_missing`), an upload whose pending object was written again between its verification and its publish (`reason: upload_changed_during_confirm` — confirm again), or an Instagram connect that failed once its one-time code was spent (`reason: instagram_connect_restart_required` — start again). The error handler also answers a Postgres foreign-key violation (`23503`, `errors:databaseReferenceConflict`) and a deadlock or serialization failure (`40P01` / `40001`, `errors:resourceBusy`) with 409 instead of a 500.                                                                                                                                                                                                                       | Services + idempotency middleware                |
| **413** | POST/PATCH/PUT — request body exceeds the size limit: 1 MiB, 5 MiB on the provider webhook receivers, 16 KiB on Meta's deauthorize and data-deletion callbacks.                                                                                                                                                                                                                                                                                                                                                 | Fastify body limit                               |
| **415** | POST/PATCH/PUT — `Content-Type` is not `application/json` (where a JSON body is expected; `application/x-www-form-urlencoded` on Meta's two callbacks).                                                                                                                                                                                                                                                                                                            | Fastify content-type parser                      |
| **422** | Mutating routes — request is well-formed but violates a business rule (including a payment method the provider declined: `reason: payment_declined`) (including a capability unavailable for an **immutable resource type** — e.g. a personal organization cannot gain members, roles, ownership transfer, or deletion), or an `X-Idempotency-Key` is reused with a **different payload** (fingerprint mismatch) or is malformed (16–255 characters of the allowed set — the same 422 on every write, the key required or not, and on an unknown path). The error handler also answers a Postgres CHECK violation (`23514`, `errors:databaseCheckViolation`) and a number out of range (`22003`, `errors:databaseNumericOutOfRange`) with 422 instead of a 500.                                                                    | Services + idempotency middleware                |
| **429** | Any route — global or per-route rate limit exhausted (`code: rate_limited`). Response carries `Retry-After` and `X-RateLimit-Limit` / `X-RateLimit-Remaining` / `X-RateLimit-Reset`. `POST /auth/login` also answers it once the caller's IP has 50 failed logins in 15 minutes — before any credential check, valid credentials included — with `Retry-After` = the window's remaining seconds. Any credentialed request on a protected route answers it once its client address has 60 failed authentications (401s) in a minute, before any credential check. Unknown URLs and failed authentication count against the global per-IP limit. An IPv6 caller is one address per /64. | Rate-limit middleware · auth service (per-IP failed-login throttle) |
| **503** | A required dependency is unavailable and the request **fails closed** rather than risk an unsafe write: the Redis idempotency store is down on a required-idempotency write (`code: service_unavailable`), the payment provider (Stripe) is unreachable or rate-limiting (`errors:paymentProviderUnavailable`), Cloudflare Turnstile cannot verify a captcha (`errors:captchaProviderUnavailable`), the OAuth provider fails during sign-in (`errors:oauthProviderUnavailable` — a provider refusing the code or token stays a 401), another integration's circuit is open (`errors:externalServiceUnavailable`), Instagram is down, failing or throttling (`reason: instagram_unavailable`, with `Retry-After`) or its app settings are unset (`reason: instagram_not_configured`), the database cannot give the request a connection — it refuses or does not answer, or none frees up before `DATABASE_POOL_ACQUIRE_TIMEOUT_MS` (`Retry-After: 5`) — or the service is shedding load. Carries `Retry-After` when the wait is known (an open circuit: its remaining open time). Unlike a 500, the detail is the real, translated message and the response is not sent to Sentry — the outage is alerted where it happens (the circuit opening). Retry once the dependency recovers. | Idempotency middleware · error handler (open circuit, Stripe) · captcha pre-handler · OAuth providers · database contexts (`runPooledUnitOfWork`) · overload guard |
| **500** | Unexpected failure. Never intentional: the never-5xx fuzz gate (`src/tests/security/`) fails CI if any route 5xxes on malformed input. External message is generic; details go to Sentry — a database failure only as `{ name, code, constraint, table }`: the logger, Sentry and the dead-letter ledger never carry its statement, bound values or row detail (`sanitizeDatabaseError`, `sensitive-redaction.util.ts`, C-1).                                                                                                                                                                                                             | Error handler                                    |

**Decision guide for a new failure path:** is the request unreadable → 400/413/415; unauthenticated → 401; authenticated but not allowed → 403; thing doesn't exist → 404; valid request colliding with current state → 409; valid request breaking a business rule → 422; too fast → 429. If none fit, you are probably about to invent a status — don't; map it to the closest above.

**400 vs 422:** 400 = the request itself is malformed (shape). 422 = the request parses fine but the system rejects its meaning (semantics). **409 vs 422:** 409 = conflict with existing state (try again may succeed after state changes). 422 = the payload's logic is wrong, or the target resource **type** makes the capability permanently unavailable — retrying an identical payload always fails (e.g. a personal organization can never have members/roles/ownership-transfer/deletion because the organization `type` is immutable; the centralized guard is `assertTeamOrganization(...)`).

## Error body shape

All error statuses share one envelope (`src/shared/middlewares/core/error-handler.middleware.ts`):

```json
{
  "error": {
    "type": "validation_error",
    "code": "validation_error",
    "detail": "Invalid request body",
    "errors": [{ "field": "body.email", "message": "Invalid email format" }]
  },
  "meta": { "request_id": "018f2c7a-3b4d-4e5f-9a6b-7c8d9e0f1a2b" }
}
```

Fields: `type` is `request_error` or `validation_error` (always present); `code` is the status-class slug (e.g. `validation_error`, `conflict`, `not_found`); `detail` is the human, i18n-resolved message (per `Accept-Language`); `errors` (the per-field array) appears on validation (400) only — schema-validated input names its location and path (`body.email`, `querystring.limit`, `params.plan_id`; the location alone for a request-level issue), and a strict schema reports **one entry per unknown key** (`querystring.page`, `body.public_id`) with a localized `Unrecognized key: "…"` message; `documentation_url` is added when `API_DOCS_BASE_URL` is configured. `request_id` (under `meta`) is the server-minted UUID (also echoed as `X-Request-Id`) — quote it in support tickets. Every error path — including the idempotency-middleware 409/422/429/503 responses — emits this same `{ error, meta }` envelope.

**`error.reason` (optional, machine-readable):** select 4xx errors — and a 503 that names which dependency is down or unset — carry a stable snake_case `reason` sub-code so the frontend can branch on the specific cause without parsing the human `detail`. It is **additive** (present only where set). A **503 keeps** its reason (launch D34 — `instagram_unavailable` means retry later, `instagram_not_configured` means an operator must set the Instagram app; a reason names a cause, never internal detail, so the overload guard's shed signal is logged, not set as a reason); **every other 5xx omits it** (a 500's detail is masked and captured). `code` stays the status-class slug (e.g. `conflict`); `reason` is the specific cause. Current slugs: `membership_already_exists`, `seat_limit_reached`, `organization_slug_exists`, `invitation_revoked`, `invitation_already_accepted`, `invitation_expired`, `disposable_email`, `mfa_required` (403 — the active organization's security policy requires MFA and this session has not proved a second factor; step up with `POST /auth/me/mfa/verify` or enroll, then switch organization again), `payment_declined` (422), `default_organization_unavailable` (422 — `PATCH /users/me/settings` named a `default_organization_id` that is not an active organization the caller actively belongs to), `payment_provider_resource_missing` (409), `upload_changed_during_confirm` (409), `missing_permission` (403 — the caller's role, or API key, lacks a code the route or the action needs: every route-level permission gate; launch D83), `owner_membership_fixed` (403 — the organization owner's status or main role cannot change and they cannot be removed; transfer ownership first), `owner_cannot_leave` (403 — the owner cannot leave), `owner_only` (403 — only the organization owner may do this: delete the organization, change its `status`), `slug_read_only` (422 — `PATCH /tenancy/organization` with a `slug`: the slug is made once from the name at create and never changes), `membership_not_restorable` (409 — `POST …/memberships/{membership_id}/restore` on an end only the person can undo: they left, deleted their account, declined, or their invite expired or was revoked), `owner_role_fixed` (403 — the codes of the role the owner holds as their main one cannot change), `system_role_fixed` (403 — a system role cannot be renamed or deleted), `role_locked` (403 — a locked role's codes cannot change: Owner, Admin, Editor, Viewer), `custom_roles_off` (403 — custom roles are switched off in this product (feat-instagram-dm-sending TN3): creating, editing, deleting or restoring a role or replacing its codes, after the permission gate; and a membership `POST`/`PATCH` whose `role_ids` names more than one role or one that is not a system role; detail `errors:customRolesOff`), `organization_read_only` (403 — a guarded product write from an organization without a paid plan whose grace has ended; reads, billing, auth, user, tenancy and upload stay open — `GET /auth/me/context` reports it as `active_organization.plan_access`; only while `BILLING_READ_ONLY_ENFORCED` is on), `team_organization_required` (404 — a team-only read on a personal organization; a read is never a 422, while the same surface's writes answer 422 through `assertTeamOrganization`. Thrown by `assertTeamOrganizationForRead` in `organization-capability.ts`; detail `errors:notFound` naming `errors:resources.Team organization`), and the Instagram account's (launch routes-final § 1.A, § 1.C, IA10): `instagram_code_invalid` (422 — Instagram refused the connect code: expired, used, or for another redirect address; restart "Connect Instagram"), `instagram_account_not_professional` (422 — a personal Instagram account), `instagram_scopes_missing` (422 — a needed permission was not granted on Instagram's consent screen), `organization_already_has_instagram_account` (409 — the organization has another account that is not revoked), `instagram_account_connected_elsewhere` (409 — this Instagram account is live in another organization), `instagram_connect_restart_required` (409, never with `Retry-After` — `POST /app/social/instagram/connect`: Instagram failed, throttled or its circuit opened after its one-time code was spent, and nothing of this connect is stored; a retry of the same code could only answer `instagram_code_invalid`, so restart "Connect Instagram" (launch D56) — an outage of the code exchange itself is still `503 instagram_unavailable`; detail `errors:instagramConnectRestartRequired`), `instagram_not_connected` (404 — no account that is not revoked; detail `errors:notFound` naming `errors:resources.Instagram account`; a **409** with the same reason and detail on `POST /app/automations` — creating an automation needs the organization's connected account, a state that passes once one connects, launch AU27), `instagram_reconnect_required` (404 — the post and story pickers, `GET /app/social/instagram/media` and `/stories`: the account is `expired` or `error`, or Instagram just refused its token and the account was moved there; a GET is never a 409, so the frontend branches on this reason and shows the reconnect card; detail `errors:notFound` naming `errors:resources.Instagram account`), `instagram_unavailable` (503 with `Retry-After` — Instagram down, failing or throttling), `instagram_not_configured` (503 — `INSTAGRAM_APP_ID`, `INSTAGRAM_APP_SECRET` or `INSTAGRAM_REDIRECT_URI` unset; Meta's two callbacks need only `INSTAGRAM_APP_SECRET`) and `instagram_signed_request_invalid` (400 — Meta's deauthorize or data-deletion callback, `POST /app/social/instagram/deauthorize` and `/data-deletion`: the form's `signed_request` is missing, doubled, malformed or wrongly signed, names another algorithm than `HMAC-SHA256`, or carries no `user_id`; a bad provider signature is a 400, as the Stripe webhook's; nothing changes), and the contacts' (launch routes-final § 2.9): `contact_not_found` (404 — `DELETE /app/contacts/{contact_id}` named no contact of this organization: absent, another organization's, or already erased — an erase is never undone; detail `errors:notFound` naming `errors:resources.Contact`), the automations' (launch routes-final § 3.A.9): `automation_not_found` (404 — `GET`, `PATCH` or `DELETE /app/automations/{automation_id}` named no live automation of this organization: absent, deleted or another organization's; detail `errors:notFound` naming `errors:resources.Automation`), `next_post_window_overlap` (409 — a live, waiting "next post" automation's window overlaps another of the same Instagram account that shares a keyword, or either has none; the detail names the other automation, the keyword and its window — `errors:nextPostWindowOverlap` / `errors:nextPostWindowOverlapAnyComment`; no `errors[]`), `next_post_already_linked` (409 — `PATCH` changed a linked "next post" automation's window, `target_scope` or target ids), and the Instagram webhook's (launch routes-final § 4.A.9 — Meta reads only the status): `invalid_webhook_verify_token` (400 — `GET /app/social/instagram/webhook`, Meta's subscription check: `hub.mode` is not `subscribe` or `hub.verify_token` differs from `INSTAGRAM_WEBHOOK_VERIFY_TOKEN`; a failed webhook proof is a 400, never a 403), `invalid_webhook_signature` (400 — `POST /app/social/instagram/webhook`: `X-Hub-Signature-256` missing, malformed, or not the HMAC-SHA256 of the raw body with the app secret) and `instagram_webhook_not_configured` (503 — the verify token (subscription check) or `INSTAGRAM_APP_SECRET` (delivery) unset) — extend as new FE-relevant cases arise by calling `AppError.withReason('<slug>')` at the throw site.
