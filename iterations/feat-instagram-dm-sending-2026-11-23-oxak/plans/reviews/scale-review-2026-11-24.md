| 1 | DB connection budget (per server + cluster) | The plan's worker "places" cannot boot under the repo's budget rules. The plan wants intake 5→20, fast 40→100 and slow 40→50 places per server, all sharing a **20-connection pool** plus a 5-connection webhook pool (plan:L4439–L4445, L6160, L6912). The repo blocks this in three ways. (a) `WORKER_CONCURRENCY_*` is capped at 20 (`env-schema.ts:934–940`), and SN2 falls the new send queues back to `WORKER_CONCURRENCY_INSTAGRAM` (RF:L2652). So the budget overstates real use by about 5–10×. | blocker | Add an **in-process DB semaphore** for the send, intake and tasks workers, for example 16–24 slots per process, shared, with a 2 s acquire then put the ticket back. **Repository-rule consistency.** No violations found:
- **Postgres is the only source of truth.** After P32, Redis holds only tickets that can be rebuilt, the advisory gate-1 counts, copies and the connect state (P26).
- **Workers are pull-based.**
- **Every tenant job carries `organizationPublicId`.** K8, plan:L4255; the cross-organization repair reads are exempted in SNC5.
- **No `NODE_ENV` branching.** SN7 uses `SENDING_ENABLED` with a static default of `false`, and a production `.refine()` for `SENDING_ENVIRONMENT_ID`.

The only rule conflicts are the ones in findings 1 (the budget guard) and 18 (the `noeviction` guard).

## Already well handled

- **Postgres decides every limit.** Gate 2, the month count and `sending` are set in one claim commit. Redis is advisory and is never called inside a transaction (plan:L5706–L5745, SN3).
- **One lock order, contact → automation → runs.** Any out-of-order lock uses `skip locked`, and a test races two intake jobs on one contact (WH26, plan:L6097–L6132).
- **Intake wake-ups cannot be lost.** It uses per-account deduplication with `keepLastIfActive` (`instagram-webhook.queue.ts:76`), and is never paused by a provider outage (F3, WH25).
- **Messages are split by the run's start week.** Each ticket carries that key, so every lookup reads one part, and dropping a part replaces bulk deletes for the biggest table (SN17).
- **One clock: Postgres `now()`.** Delays are computed from Postgres time, and each server checks its own clock (plan:L6163–L6168, WC-23).
- **A restored copy never sends.** `SENDING_ENABLED` defaults to false and the environment-id row is created only when missing (SN7, D20).
- **No `unknown` send goes again by itself.** The 120 s lease and the shared `saveSendResult` retried inside the send cover it, without Redis save-result jobs (SN4, D17).
- **DLQ auto-replay is an allowlist.** Send tickets are never replayed outside the lane rules (`dlq-replay.util.ts:43–46`).
- **The rate limiter keeps working during a Redis outage.** It falls back to in-memory counting instead of failing open or closed, so the webhook still answers (`rate-limit.middleware.ts:89–125`).
- **Tokens are protected.** They are encrypted with a versioned keyring, read only on the client path, sent with `appsecret_proof`, and never put in jobs or logs. The webhook uses HMAC over the raw body plus an 8-day replay guard and the key table (WH9).
