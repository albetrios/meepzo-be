## Notes and open questions

1. **Launch WC-5 (start the automations queued behind an email)** — the plan neither keeps nor drops it; it
   now speaks of "ask once across runs" (plan:L4960–L4974). Kept unchanged here until the route review says
   otherwise (finding).
2. **No owner "stats" job** — the daily line and banners are read on request (RC-35) from the counts and a
   10-second copy, not made by background work.
3. **Team "suspend account"** has no background work: a column now, the route later ([P18](decisions.md)).
4. **Two owners of clean-up** — the plan has the every-minute pass delete minute counts (WC-20) and a daily
   job delete tag events and month counts (WC-54) (plan:L6072 vs L6081); kept as written — both are
   pieces of the one repair family (SN6).
5. **Dropped by [P32](decisions.md):** the send-result retry and the webhook buffer drain (were WC-10,
   WC-11) — a result save is retried inside the send, and when Postgres is down the webhook answers
   500 / 503 so Meta delivers again.
6. **The repair runs without the plan's shared helper slots** — settled ([P73](decisions.md), SNQ1):
   each repeating tick already goes to one server, and the two per-server duties (WC-21, WC-23) need no
   slot; `db-changes.md` drops `sending_helper_slot`. No row was about the slots, so none is removed.
7. **F3 — intake is never paused by a provider outage** ([P47](decisions.md), adopted from the webhook
   review): the launch's intake worker paused on an open Instagram circuit, yet most events need no
   Instagram call. Here only a provider call checks the circuit — per provider, per job — so an outage
   never stops intake from saving its decisions; the sends then wait on their lanes' stops (WC-22). This
   settles coverage R10.
8. **F5 — one lock order in every intake path** ([P47](decisions.md)): the three intake passes of one
   account (chat events, Live comments, comments) and the tag-event pass can touch the same contact at
   once (her DM and her comment); each takes its locks contact → automation → runs, and one test races two
   intake jobs on one contact.
9. **The token check is the connection's** ([P47](decisions.md)): it is the one common background piece
   of the channel split; a later Facebook Pages login under the same Meta connection is checked by the
   same pass (P41).
10. **The retired-plan notice is WC-59's** ([P80](decisions.md), [P99](decisions.md)): the 15-minute
    plan-state check finds a subscription still on a switched-off row, moves it down to Free's once and
    emails once per subscription; the notice is read on the plan-access read (`is_plan_choice_required`,
    route 108, RC-64) until it picks Creator or Studio — no repeat email. (Was WC-66, a one-time pass at
    the release with its notice on RC-56, folded in by P99.)
11. **`SENDING_ENABLED`** ([P74](decisions.md)) is `true` in `.env.example`, so the lanes send on a
    developer's machine; the schema default stays `false`, so a deploy sends nothing until it is set.
12. **The send work runs on its own** ([P91](decisions.md), S1): the sending lanes (WC-5–WC-8) run as their
    own service, apart from the API, so each side's database connections are sized on their own; the send,
    intake and task work share an in-process database limiter (about 16–24 places a process — a piece that
    waits over 2 s for one goes back to wait its turn), and the connection budget counts that limiter, not
    how many pieces run at once. The arithmetic for now and for 1,000 accounts goes into the resource
    limits doc. Kickoff names the service and the settings.
13. **A rollback keeps sending** ([P95](decisions.md), S16): a server older than the minimum compatible
    settings version takes no send tickets; an older but compatible one does. The rollback step and how the
    host rolls several servers go into the path-to-production rollback.
14. **Kickoff defaults** ([P97](decisions.md)): background work the scale review's Fix column sets and
    kickoff builds — the new-contact profile read moved to a low-priority task and several comment-intake
    passes per account, the contact lock keeping order (S11, WC-1, WC-2); the tasks split into Meta-calling

    WC-36); a cap per organization on fast sends in flight (S21, WC-7); no `queued` mark after the webhook's
    save (S25, WC-12); the token check re-encrypts a token still on an old key (S26, WC-34); the waiting
    estimate stored by its 10-minute run (S29, WC-24). Any difference goes into `AS-BUILT.md`.
15. **After launch, operations** ([P98](decisions.md)): pausing the send work when Postgres is slow and the
