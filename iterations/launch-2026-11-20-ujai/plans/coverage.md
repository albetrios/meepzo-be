## Findings

### Drop vs repository rules (code today)

1. **API paths.** Every route today is `/api/v1/<domain>/…` (`docs/routes.txt`); the drop uses `/app/…` (schema-routes.md:24, schema-routes.md:72). The domain segment follows Q1. → [D1](decisions.md), [D20](decisions.md)
2. **No `app` schema.** Postgres schemas today are auth, tenancy, billing, notify, audit and upload; `app.` is already the prefix of the per-request settings (`app.current_organization_public_id`, `app.global_retention_cleanup`). The drop puts every table in `app` (schema-routes.md:682, schema-routes.md:160-165) → the domain is a Step 4 question (Q1). → [D1](decisions.md)
3. **Permission code casing.** Codes are kebab-case `<resource>:<action>` (`api-key:read`, `audit-log:read`, `notification-policy:manage`, `docs/routes.txt:265`); `instagram_account:read` / `:manage` (schema-routes.md:132-133) → `instagram-account:read` / `:manage`. → [D20](decisions.md)
4. **`webhook:read` clash.** `webhook:read` / `webhook:manage` already gate notify's outbound webhooks (`GET /api/v1/notify/webhook-events`, `docs/routes.txt:100`). The drop reuses `webhook:read` for Instagram webhook events (schema-routes.md:33, schema-routes.md:139, schema-routes.md:579): one grant would open both (Q2). → [D4](decisions.md)
5. **Roles.** Only two system roles exist: Owner and Admin (Admin is a locked preset); other roles are custom. The drop's Member column (schema-routes.md:143-150) has no target, and already-provisioned team organizations need the new codes on their Owner and Admin roles (Q2). → [D2](decisions.md), [D3](decisions.md)
6. **Folder layout is agent-os's.** The drop fixes folders (`social`, `instagram`, `automations`, `contacts`, schema-routes.md:45-56); sub-domain folders must carry the domain or resource prefix, and the plan names no folders — agent-os decides at kickoff.
7. **Cross-organization lookups under row-level security.** Webhook routing by `instagram_user_id` before the organization is known (schema-routes.md:526), the "connected elsewhere" check (schema-routes.md:456), one Instagram account across all organizations (schema-routes.md:741) and webhook events with no organization (schema-routes.md:814) all read across organizations. Requirement: these lookups work without opening any other organization's data; how is agent-os's (Q19). → [D21](decisions.md)
8. **Token isolation.** "Not readable by the normal app session; only the Instagram client reads it" (schema-routes.md:766) has no stated pattern in the repository today. The encryption key matches the existing server secrets key (schema-routes.md:773) — reuse it (Q19). → [D21](decisions.md)
9. **Comment logs without references.** `automation_run_id` and `contact_id` have no foreign key (schema-routes.md:953, schema-routes.md:962-963), against the composite-reference rule the drop itself sets (schema-routes.md:685) — agent-os decides (Q19). → [D21](decisions.md)
10. **Reuse the Stripe webhook ledger.** `src/domains/billing/sub-domains/stripe-webhook/` (`POST /api/v1/billing/webhook`, `docs/routes.txt:78`) already stores each provider event once by its id, keeps the raw body for the signature, reclaims stuck rows, caps attempts and prunes old rows. Its raw-body registry is Stripe-named; the reuse rule says improve it for both receivers, never a second copy (evidence only, not a design).
11. **Team-only routes exist.** The O column (`team`, 422 on personal, `docs/routes.txt:12`) already carries "team workspaces only" (schema-routes.md:74).
12. **Public id prefixes are free.** `iga`, `iwe`, `aut`, `con`, `run`, `acl` (schema-routes.md:160-165) clash with none of today's (usr, org, mem, inv, rol, key, pol, ses, am, wac, ntf, whk, pln, sub, upl, exp, bug, wda, evt, aud).
13. **Audit action names.** The repository writes `<domain>.<resource>.<verb>` in the present tense (`notify.webhook.create`, `billing.subscription.create`); the drop writes `instagram_account.connected`, `automation.created` / `.updated` / `.deleted` (schema-routes.md:458, schema-routes.md:614, schema-routes.md:632, schema-routes.md:640) (Q18). → [D20](decisions.md)
14. **Setting names.** The legacy settings break three repository rules: `IG_SEND_DELAY_*` abbreviates (PRD.md:152), `APP_SECRET` is a fallback for one behaviour (PRD.md:17), and queue names carry NODE_ENV (PRD.md:40). The verify token, app id and redirect URI are not named at all (schema-routes.md:509, schema-routes.md:440) (Q18). → [D20](decisions.md)
15. **Webhook rate limit.** The repository's Stripe receiver runs under a webhook rate-limit preset; the drop says "no rate limit" (schema-routes.md:84) — agent-os decides (Q19). → [D21](decisions.md)
16. **Process split.** The legacy webhook and workers share one process (PRD.md:9); the repository runs a separate worker process with a fixed queue catalog and worker registry, and workers are pull-based (Q19). → [D21](decisions.md)
17. **Words.** The drop says "workspace"; the repository says "organization" (full names in prose and identifiers).

### Inside schema-routes

1. **Two step-name lists.** `automation_runs.current_step` (schema-routes.md:1019: keyword_match, comment_reply, …) and `automation_comment_logs.current_step` (schema-routes.md:1025: public_reply, opening_dm, …) name the same steps differently (Q17). → [D19](decisions.md)
2. **Two names for the button wait.** `waiting_for` is `opening_message_button` on runs (schema-routes.md:927, schema-routes.md:1020, schema-routes.md:553) and `button` on comment logs (schema-routes.md:987, schema-routes.md:1026) (Q17). → [D19](decisions.md)
3. **`unsupported` has no rule.** The skip-reason list has `unsupported` (schema-routes.md:1012) but §6.5 step 4 does not (schema-routes.md:528); kind `unknown` (schema-routes.md:1010) has no handling either (Q16, Q17). → [D18](decisions.md), [D19](decisions.md)
4. **"Straight away" after writes.** §6.5 answers 200 "straight away" (schema-routes.md:530) after steps 2–5 that look up, insert, skip and queue rows (schema-routes.md:526-529) — is the answer sent before or after the rows are stored? (Q13) → [D15](decisions.md)
5. **Lists typed as plain text.** `InstagramWebhookEvent.event_kind`, `status` and `skip_reason` are typed `string` (schema-routes.md:275, schema-routes.md:277, schema-routes.md:278) while the query (schema-routes.md:268-269) and §9 define them as value lists (Q17). → [D19](decisions.md)
6. **Event key gaps.** The key is defined only for comments, messages and button clicks (schema-routes.md:817); a button click may have no `mid` (schema-routes.md:425); a read receipt carries the `mid` of the message it read (schema-routes.md:426), so its key would collide with that message; and the key is unique across all accounts (schema-routes.md:825), so a DM between two connected accounts (echo on one side, message on the other) collides (Q13). → [D15](decisions.md)
7. **An organization can never switch accounts.** One account per organization is unique for every status (schema-routes.md:741), a different account answers 409 (schema-routes.md:455), and nothing ever sets `revoked` (schema-routes.md:221) (Q3). → [D5](decisions.md)
8. **Final message.** Required on create (schema-routes.md:317, schema-routes.md:606) but empty-able in the table and the response (schema-routes.md:857, schema-routes.md:358) (Q17). → [D19](decisions.md)
9. **The DM keyword flag.** `is_dm_keyword_trigger_enabled` defaults to true for every trigger type (schema-routes.md:307, schema-routes.md:844); turned off on a `dm` automation it can never run; on comment and story-reply automations it lets a DM start them (schema-routes.md:537) (Q12). → [D14](decisions.md)
10. **No log for DM and story-reply runs.** Run step 1 writes a comment log for every run (schema-routes.md:545), but comment logs are for comment triggers only (schema-routes.md:953); a failed DM or story-reply run keeps only run fields that roll back with it (schema-routes.md:929, schema-routes.md:938) (Q14). → [D16](decisions.md)
11. **`instagram-account:read` reads no account.** It allows only browsing posts, reels and stories (schema-routes.md:132); no route returns the account itself (Q3). → [D5](decisions.md)
